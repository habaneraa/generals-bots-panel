## 改动与行为边界

### 1. 同步 JSON 写入只维护一份

[运行配置](../../apps/server/src/storage/config.ts)与[Player 注册表](../../apps/server/src/storage/player-registry.ts)原先分别实现临时文件、权限、JSON 序列化、重命名和失败清理，修改策略需要同步维护两份。

现在共用 33 行的[内部函数](../../apps/server/src/storage/atomic-json.ts)：

- 同目录独占创建临时文件，权限仍为 0600；缩进 JSON 与末尾换行保持不变。
- 保留注册表替换前的 `fsync`；配置保存不增加该步骤，避免改变同步成本与失败点。
- schema 校验仍由调用者负责；配置只在替换成功后更新内存缓存。
- 只有成功创建临时文件后才尝试清理，避免创建冲突时删除其他写入者的文件。
- 清理仅忽略 `ENOENT`，双重失败保留两个异常；不宣称 `rename` 或单文件 `fsync` 能保证任意断电场景的数据持久性。

[9 项回归](../../apps/server/src/storage/atomic-json.test.ts)覆盖写入、同步、重命名失败，真实目录冲突，清理失败，独占创建冲突，以及配置缓存不提前提交、失败后可继续保存。现有格式、权限、重启与非法配置测试继续保留。

### 2. 录像清理失败不再被吞掉

[录像存储](../../apps/server/src/storage/replays.ts#L49-L65)原先无条件忽略临时文件删除失败，可能丢失临时录像遗留的诊断。

现在清理成功或文件已不存在时仍抛出原始保存异常；其他清理失败使用 `AggregateError` 保留两个原始对象。控制器目前只记录异常的 `message`，因此聚合消息也包含两个文件系统错误，沿用现有 `warn` 日志即可看到原因，无需修改控制器或新建日志框架。

[3 项回归](../../apps/server/src/storage/replays.failure.test.ts)验证原异常身份、聚合异常顺序与消息、旧 gzip 字节与读取结果保持，以及临时文件是否遗留。现有“录像失败不改变正常胜负、成功后才标记本地录像”回归仍通过。正常 gzip 编码、文件权限与异步保存流程没有改变，也没有将异步录像纳入同步 JSON 抽象。

### 3. 表单卸载后不再影响新工作区

复现了一个真实生命周期遗漏：[校验 hook](../../apps/web/src/hooks/useRunConfig.ts)在无效校验后排入动画帧，但没有保存和取消句柄。连续两次无效校验后切换 keyed Player 工作区，旧回调仍会通过全局表单 ID 滚动新工作区。

现在每次校验先取消旧帧，卸载时取消未执行任务，执行后清空句柄；正常聚焦首个错误字段与回退滚动保持不变。没有增加共享调度器或通用异步 hook。

[5 项回归](../../apps/web/src/hooks/useRunConfig.test.ts)覆盖渲染后聚焦、回退滚动、重复校验合并、工作区替换隔离，以及修正参数后成功校验清除旧错误和焦点任务。
